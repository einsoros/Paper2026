# 00-PLANW — 목적 · 범위 · 운영원칙

> 갱신규칙: 운영원칙·범위가 바뀔 때만 수정한다. 연구내용은 여기에 쓰지 않는다.

---

## 1. 정체성

PlanW는 석사학위논문(Paper2026)을 위한 **독립적인 신규 연구 프로젝트**다.

- 이전 Plan A/B/C의 대화·파일·판단·연구모형을 알고 있다고 가정하지 않는다.
- 이전 프로젝트를 읽거나 복원하거나 상속하지 않는다.
- 과거 파일을 읽어 현재 방향을 추론하지 않는다.
- 필요한 정보는 이 프로젝트에서 사용자와 GPT가 명시적으로 제공하는 것만 사용한다.
- PlanW 자체의 근거와 원전으로 독립적으로 연구를 구축한다.

## 2. 연구 작업 원칙

PlanW는 HRM/OB(인적자원관리/조직행동, Human Resource Management / Organizational Behavior)의
기존 이론과 검증된 연구를 먼저 정확하게 이해하고, 그 위에서 연구모형을 구축한다.

**원칙적 순서**

1. 원전 확보
2. 원전 정독 / 사실 확인
3. construct와 이론관계 확인
4. 측정 / 척도 계보 확인
5. 후속연구 계보 확인
6. backbone 안정성 판단
7. (필요시) 최소 확장 검토
8. RQ / 가설 / 모형
9. 연구설계 / 측정계획

**금지**

- 뒤 단계의 아이디어를 앞 단계로 끌어오지 않는다.
- 새로운 변수, mediator(매개변수), moderator(조절변수), context, contribution을
  원전 확인 전에 발명하지 않는다.

## 3. 현재 범위 제한

- 이 단계에서 AI, GenAI(생성형 AI), automation, digitalization,
  algorithmic management, Human-AI collaboration을 연결하지 않는다.
- 사용자의 현업 사례를 backbone 정당화 근거로 사용하지 않는다.

## 4. 연구 판단 규칙 — 근거등급 표기

모든 기록은 다음 네 등급을 구분해 표기한다. C/D를 A처럼 표현하지 않는다.

| 등급 | 의미 |
|---|---|
| **A** | 원전에서 저자가 직접 주장/검증한 것 |
| **B** | bibliographic / metadata로만 확인한 것 |
| **C** | Claude의 해석 / 추론 |
| **D** | 아직 검증되지 않은 가설 / 아이디어 |

추가 규칙

- X/M/Y/Z는 반드시 실제 construct 이름을 함께 쓴다.
- M/Z가 없으면 **없는 것으로 기록**하고 임의로 채우지 않는다.
- 검색 부재를 research gap으로 판단하지 않는다.
- 비유의성을 관계 부재와 동일시하지 않는다.
- 측정대상, 분석수준, 평가주체, 연구맥락을 임의로 바꾸지 않는다.

## 5. 자료관리 구조 (요약)

| 층위 | 도구 | Source of Truth |
|---|---|---|
| 서지정보 · 원전 | Zotero | 정확한 서지정보, DOI, 원문 PDF, metadata, collection/tag |
| 연구논리 · 현재 상태 | Obsidian | 고정 관리문서 8개 |
| 변경이력 · 과거 상태 | Git | 커밋 히스토리 |

**PDF 확보와 원전 내용 검증은 구분한다.** PDF가 Zotero에 있다는 사실은 B등급이며, A등급이 아니다.

## 6. 파일 관리 규칙

핵심: **`새로운 연구단계 = 새로운 파일`이 아니다.**

| 변경 유형 | 수정 대상 |
|---|---|
| 연구모형 변경 | 01-RESEARCH-MODEL.md |
| 이론 근거 추가 | 02-THEORY.md |
| 논문 추가 / 판정 | 03-LITERATURE.md |
| 척도 확인 | 04-MEASUREMENT.md |
| 중요 결정 | 05-DECISIONS.md |
| 진도 변경 | 06-PROGRESS.md |
| 인계 상태 변경 | 99-HANDOFF.md |

- 새 `.md` 생성은 원칙적으로 금지한다. 기존 8개 문서로 관리할 수 없는 명확한 필요가
  있을 때만 사용자와 협의 후 생성한다.
- 날짜별 action-item, stage별 결과, 후보별 파일, 매번의 review 파일을 만들지 않는다.
- 과거 버전 보존을 위해 stage 파일을 만들지 않는다. 과거 상태는 Git history로 보존한다.
- **파일명에 날짜를 넣지 않는다.** `2026-09-13-review.md` 같은 이름을 만들지 않는다.
  파일명은 `NN-NAME.md` 형식만 사용한다. 갱신 시점은 파일명이 아니라 헤더로 표시한다.

### 문서 헤더 표준

8개 문서 전부 첫 줄부터 다음 YAML frontmatter를 유지한다. Obsidian 속성(properties) 패널에
그대로 노출되므로, 파일을 열지 않고도 최신 갱신 시각과 현재 상태를 볼 수 있다.

```yaml
---
문서: 03-LITERATURE
역할: 선행연구 대장 — 역할 · 원전 확인 여부 · 채택/보류/탈락
갱신: 2026-09-13 07:25 KST
핵심: 등록 1편 · 원전 확인 0편 · 채택 0편
---
```

- `갱신` — **분 단위 시각과 KST 표기까지** 적는다. 하루에도 여러 번 갱신되므로 날짜만으로는
  최신 여부를 판별할 수 없다.
  **갱신 시각은 파일을 열거나 오탈자를 수정한 시간이 아니라, 해당 문서의 연구상태가
  실질적으로 변경된 마지막 시간으로 기록한다.** 구조·개념·판정·근거등급이 바뀔 때만
  갱신하고, 표현 다듬기·오탈자·서식 수정으로는 갱신하지 않는다.
  (그런 소소한 수정의 이력은 Git commit이 보관한다.)
- `핵심` — 한 줄. 그 문서의 **현재 상태**만 쓴다. 변경 이력이나 다음 계획을 쓰지 않는다.
- `역할`·`문서` — 문서의 기능이 바뀌지 않는 한 고정.
- frontmatter 바로 아래 H1 제목, 그 아래 `> 갱신규칙:` 한 줄을 둔다.

## 7. Mission 운영 규칙

### 7-1. 스레드 시작 게이트

새 스레드는 `99-HANDOFF.md` 를 **단독 진입점**으로 삼는다. 다른 문서를 먼저 열지 않는다.
`99-HANDOFF.md` 를 끝까지 읽고, 그 라우팅 표에 따라 필요한 문서만 연 뒤,
작업을 시작하기 전에 다음을 **한 문단으로 요약해 제출하고 멈춘다.**

1. 현재 backbone 과 그 근거등급
2. 확정된 것
3. 미확정인 것
4. 직전 Mission 결과와 **문서 반영 여부**
5. 다음에 할 일

사용자 확인 전에는 **검색 · 판정 · 파일 작성 · git 명령을 시작하지 않는다.**
확인 없이 낸 산출물은 폐기 대상이다. 단계가 끝날 때마다 같은 게이트를 다시 통과한다.

### 7-2. Mission 종료 규칙

각 Mission 종료 시 다음을 명확히 보고한다.

1. 원전으로 확인된 것
2. 미확정인 것
3. 연구구조의 변화 여부
4. 다음에 확인할 작업

**Claude 는 다음 연구방향이나 Mission 을 임의로 시작하지 않는다.**
결과를 보고하고 사용자의 다음 지시를 기다린다.

### 7-3. 스레드 종료 조건

대화에만 존재하고 8개 문서에 반영되지 않은 판정 · 사실 · 결정이 있으면 스레드를 종료하지 않는다.

- 종료 전 반드시 `06-PROGRESS.md` 와 `99-HANDOFF.md` 가 현재 상태와 일치해야 한다.
- 사용자의 판단으로 반영을 미루는 경우, **무엇이 대화에만 있는지를 `99-HANDOFF.md` §5 에
  명시**하고 해당 문서가 아직 옛 상태임을 함께 적는다. 다음 스레드가 그 문서를
  현재의 진실로 오독하지 않게 하기 위함이다.
