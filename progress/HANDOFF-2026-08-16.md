## 2. 연구 개요

```
[배경 전제] AI-인간 협업 환경 (IT 개발직 — 샘플링으로 통제)

[IV 조작]  성과 기여 귀속 모호성  (귀속 명확 vs 귀속 모호, 시나리오 2조건)
              │ H1  귀인이론 기대원리 (Weiner 1985)
              ▼
[MV 측정]  지각된 평가 불확실성
              │ H2 / H3(매개)  UMT (Van den Bos 2001)
              ▼
[DV 측정]  절차공정성 지각 (consistency + bias suppression, Colquitt 2001)
              ▲
              │ H4  MV→DV 경로(b-경로) 조절 · PROCESS Model 14
[MOD 측정] 평가 절차 명확성 (Erdogan 2002)
```

**핵심 문제의식** (`research-model.md` 확정본, `logic-architecture.md`와 동일)

> AI-인간 협업 환경에서 자기 기여 경계를 설명하기 어려워질수록, 평가 대상자는 자신이 어떻게 평가될지 예측할 수 없게 되고, 이 불확실성이 기존 평가 시스템의 절차공정성을 낮게 지각하게 만든다. 조직이 평가 절차를 명확히 설명하면 이 불확실성이 절차공정성 지각을 낮추는 정도는 완화될 수 있으나, 기여 경계의 불명확성에서 비롯된 불확실성 자체가 사라지는 것은 아니다. 즉 이 현상은 평가 시스템 자체의 결함이 아니라 산출물에서 기여가 분리되기 어려운 성질에 기인한 인식 조건의 문제이며, 따라서 절차를 개선하는 방식만으로는 그 원인에 닿지 못한다.

**확정 상태** — IV·MV·DV·MOD 정의·문항·조작 전부 확정. MOD 문항 재설계 중(§A2) · DV2 1문항 처리 미결(§4 I2). H4 존치 확정(08-13). 표본 목표 **250**(H4 상호작용 기준).

## 2-1. ★ 연구 태도 — 인수인계에서 가장 먼저 읽을 것

> **이 절은 스레드가 바뀔 때마다 유실되어 왔다.** 08-16에 「측정되지 않은」 결정이 오전에 내려졌는데 문서에 없어 오후에 되살아난 사고가 있었다. 표현 하나를 바꾸는 문제가 아니라 **연구자의 입장**이므로 여기에 둔다.

### ① 판단하지 않고 확인한다

선행연구·원전에 **귀책을 두는 어휘를 쓰지 않는다.** 사실 확인의 층위에 머문다.

```
❌ 측정되지 못한 · 편향 · 누락 · 간과 · 실패    → 원전에 대한 판단
✅ 측정되지 않은 · 남은 · 확인된 · 제시되지 않은  → 사실 확인
```

근거 사례 — Rizzo(1970)는 p.161 선정 3단계를 정상 적용했고 item 16은 ③(신뢰도 기여)에서만 탈락했다(`action-items-260816` §I8 Table 3 실측). **절차상 하자가 아니라 결과적 공백**이다. 「못한」이라고 쓰면 사실과 어긋나고 방어할 것이 하나 늘어난다.

### ② 실무 기여를 배제하지 않는다 — 중심에 두지 않을 뿐

```
경계할 것 : 주요 주장이 해법 제시가 되는 것   → 실무 리포트·분석자료로 전락
정당한 것 : 연구 결과가 실무에 갖는 함의      → 정(正)이든 부(否)든 유의미
```

⚠️ Claude가 반복한 오류 — `action-items-260816` 「실무 기여는 **우선순위 낮춤**」을 「빼는 게 안전」으로 읽었다. **우선순위 조정과 배제는 다르다.** §03 넷째 목적이 이미 양방향 서술(완화되든 안 되든 함의가 나옴)이므로, 목적에 두고 기여에서 빼면 비일관이다.

문장 기준:
| | 예 |
|---|---|
| ❌ 처방 | 조직은 평가 절차를 …해야 한다 |
| ❌ 과잉 | 새 평가 제도의 설계 방향을 제시한다 |
| ✅ 함의 | 기존 제도가 전제해 온 조건이 성립하지 않을 수 있음을 보인다. 개선의 방향을 처방하는 것이 아니라 **개선이 다루어야 할 대상**을 특정한다 |

### ③ 과잉 주장을 하지 않는다

- **「첫 시도」·「아무도 안 했다」 금지** — 반증에 취약하다. `Literature_Map` Layer 5 비교군 8편이 인접 영역에 있다

## 6-1. ★ 파일 전달·커밋 프로세스 — Claude가 매번 따를 것

> Claude는 리포에 **직접 push할 수 없다.** 파일을 만들어 내려보내면 성준님이 배치·커밋한다. 이 절차가 매 스레드 재협의되는 것을 막기 위해 고정한다.

### Claude가 지켜야 할 4가지

1. **배치 경로를 표로 명시한다** — 다운로드 파일명 → 리포 경로 → 신규/덮어쓰기
2. **바로 실행 가능한 명령을 준다** — `cd` 없이. 성준님은 항상 `Paper2026` 디렉터리에 있다
3. **리포에 들어갈 파일만 내려보낸다** — 커밋 메시지·명령어 초안은 채팅 본문에만 쓴다 (08-16에 `COMMIT-MSG.txt`를 파일 목록에 섞어 혼란을 만든 사고)
4. **예상 `diff --stat` 수치를 미리 제시한다** — 배치 사고 검증용

### 표준 절차

```bash
# ① 배치 (SRC는 다운로드 위치)
SRC=~/Downloads
cp "$SRC/<파일명>"  <리포경로>/

# ② 검증 — Claude가 제시한 예상 수치와 대조. 다르면 커밋하지 말 것
git --no-pager diff --stat
git status --short

# ③ 커밋 — 접두는 작업 기기 (mp / wp / ma)
git add <경로1> <경로2> ...
git commit -m "[mp] <제목>" -m "<본문 불릿>"

# ④ 푸시 + SHA 확보
git push
git rev-parse HEAD
```

### 검증

④의 SHA를 Claude에게 주면 `raw.githubusercontent.com/einsoros/Paper2026/{SHA}/{경로}`로 반영 여부를 확인한다.
⚠️ **`main` 경로는 CDN 캐시를 반환한다.** 08-10 작업 유실 사고의 원인.

### 주의

- 파일명에 공백·`&`가 있으면 **따옴표 필수** (예: `"Sources/Papers/Niehoff & Moorman (1993).md"`)
- ⚠️ 배치 전 `git pull`. 종료 시 미완이어도 `push`
- ⚠️ 같은 커밋을 두 번 올려 작업이 유실된 사례(08-15, A0-2) → ②의 대조를 건너뛰지 말 것
- ⚠️ frontmatter 값에 콜론(`: `) 금지 — YAML 파싱이 깨진다

### 문서화 타이밍

⚠️ **판단이 확정되면 그 자리에서 문서에 박는다.** 08-16에 오전 결정(「측정되지 않은」)이 등재되지 않아 오후에 유실됐고, 6시간 분량의 판정이 대화에만 남을 뻔했다.
- 결정 → 해당 `Analysis/` 파일 + `action-items` 해당 절 + 변경 이력 3곳에 동시 반영
- 미결은 `⬜ 탐색 중`으로 남기되 **확정된 것은 먼저 커밋**한다
